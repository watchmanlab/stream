Exactly! You've identified a critical TypeScript behavior.

When TypeScript instantiates generics, it evaluates defaults in order. If a generic is **not used** in the type's structure (class extends, properties, methods), TypeScript may:

1. **Skip computing it** during type instantiation
2. **Compute it lazily** only when explicitly referenced
3. **Drop it from the type identity** for structural comparison

So when you have:
```typescript
VALUE = Stream.ExtractValue<SOURCE>,
CLEAN_VALUE = Stream.ExtractCleanValue<VALUE>,  // depends on VALUE
```

But `VALUE` isn't used in the class body, TypeScript's instantiation algorithm gets confused about the dependency chain. It might compute `CLEAN_VALUE` before fully resolving `VALUE`, or it might use a cached/partial version of `VALUE`.

This is why you're seeing pollution - the unused `VALUE` generic creates an unstable dependency that causes TypeScript to compute `CLEAN_VALUE` incorrectly.

**The fix**: Remove unused generics entirely. Every generic should either:
1. Be used in the type structure (extends clause, properties, methods)
2. Be explicitly referenced by other generics that ARE used

- The multiplexing architecture

**Merge is a routing primitive**, not a filtering primitive. It should preserve ALL information from all sources.

## The Type Inference Problem

**Return style (perfect inference):**
```typescript
.pipe(map(v => {
  if (v === 3) return Stream.err("kechmahaja" as const);
  return v.toFixed();
}))
// ERROR generic infers as: "kechmahaja"
// stream.map.errors → ErrorEvent<..., "kechmahaja">
```

**Throw style (loses inference):**
```typescript
.pipe(map(v => {
  if (v === 3) throw Stream.err("kechmahaja" as const);
  return v.toFixed();
}))
// ERROR generic infers as: never (TypeScript can't infer from throw)
// stream.map.errors → ErrorEvent<..., never>
```

## Why TypeScript Can't Infer

**Return type inference:**
```typescript
function mapper(v: number) {
  return Stream.err("fail");  // ← Return type includes this
}
// Inferred: (v: number) => string | Stream.Err<"fail">
```

**Throw doesn't affect return type:**
```typescript
function mapper(v: number) {
  throw Stream.err("fail");  // ← Not part of return type
  return v.toFixed();
}
// Inferred: (v: number) => string
// The throw is invisible to type inference!
```

## The Trade-off

**Return style:**
- ✅ Perfect type inference
- ✅ Literal types preserved
- ✅ Full type safety
- ❌ Requires explicit return

**Throw style:**
- ✅ Convenient (early exit)
- ✅ Familiar (exception-like)
- ✅ Still caught and handled
- ❌ Loses type inference
- ❌ ERROR generic becomes `never`
- ❌ Must manually specify generic if you need types

## When Throw Is Fine

**Simple cases (don't care about error types):**
```typescript
.pipe(map(v => {
  if (invalid) throw Stream.err("failed");
  return transform(v);
}))
.pipe(catchError(err => {
  console.log("Something failed");  // Don't need typed detail
}))
```

**When you manually specify the generic:**
```typescript
.pipe(map<number, string, "validation_failed">(v => {
  if (invalid) throw Stream.err("validation_failed" as const);
  return transform(v);
}))
// But this defeats the "zero explicit typing" goal!
```

## When Return Is Required

**Complex error handling:**
```typescript
.pipe(map(v => {
  if (v < 0) return Stream.err("negative" as const);
  if (v > 100) return Stream.err("too_large" as const);
  if (v === 13) return Stream.err("unlucky" as const);
  return v.toFixed();
}))
// ERROR generic: "negative" | "too_large" | "unlucky"

.pipe(catchError(err => {
  if (err.detail === "negative") { /* handle */ }
  if (err.detail === "too_large") { /* handle */ }
  if (err.detail === "unlucky") { /* handle */ }
  //         ^? Autocomplete works! Literal types preserved!
}))
```

**With throw, you lose all this type information.**

## The Design Decision

**You support both because:**
1. **Return style** - For users who want perfect type safety (your target audience)
2. **Throw style** - For users coming from exception-based code (migration path)

**But the library encourages return style** through:
- Better type inference
- Better autocomplete
- Better error discrimination
- The "zero explicit typing" promise only works with return style

**Throw is a convenience escape hatch, not the primary API.** 🎯

This is good design - support multiple styles, but have a clear "blessed" path. The type system naturally guides users toward the better approach (return style) because it just works better. 💪
