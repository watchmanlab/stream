the current work is a result of nearly 2 years dedicated exclusively to it, and a result of 300+ iteration from scrach and rethinking from first principle.

it began with a simple push based reactive library, then rebuild it using exclusively `async generator functions` with support for push using a queue per iterator, and i found that triggering the event loop microtask each value emitted or consumed is a wast. and i kept alterning between hot and cold implementation and all their variation,an what i found is `hot` is always related to storing a user code in some way, so we can call it hot=functions-driven ,and `cold` is mainly related to get values mean that cold= data-driven... of course this my experience .

some of my iterations that worth mention are:
1-`push based` :user register a callback and push will broadcast to all listeners, this way creating a chain is just a subscription to a stream and push down and of course we can delay the registration to avoid unecessary computation by wiring the streams after we have a listeners triggers.
this approach has many drawback like backpressur and memory heavy since the producer will dictate the rate until we add some buffering so at the end we will found as making it pull based.
2-`pull based using async generators`: at first this approach seems elegant anf the code is beautiful but i passed 8 months refining it and i hit many walls , like the sequential nature of it and the bridge to push require queueing and some intermediate promises that kill performances and even if its lazy and use less memory than the push based if its just pull based ,,the bridge to push will make it use more memory and cpu and each transformer add another level of nesting async generators,,so i discard it.
4-`pull-on-push`: this one is the trickiest one,, i jumped between many diffrent architectures and implementations to get it right,, the bottom line is i found that i need my custom protocol like async generator but it need to support both sync and async flows,, and there is many way to achieve that protocol ,, the first implementation for it is to request value that can be promise or raw value like this snippet "const v = consumer.next()" so its like a iterator protocol that can yield a promise or a value ,,and it work fine but the draw back is is a promise aware and this is the problem ,, because making a protocol none data agnostic mean that we will hit a wall somwhere ,, this is from my experience,, since this awernes will add up on higher layers and the messy things like branching and implementation variants begin to appear ,,, even though my first user facing API still the same across all the implementations since in my opinion is an algebraic API (stream,pipe,transformers) and i can tell that we can express anything with those three primitives.
The second protocol implementation is using callbacks ,, so instead of requesting values we register the desired callback but we request its execution , and that's the big difference ,,, this way we have the velocity of push based but its pull based hence the name of `pull-on-push` ,, so the protocole is same as iterator but different ,, and i insist on regitering the callback at the creation of my custom iterator and not on each next call ,, the reason is simple , immutability and performance since the JIT will optimize the listener like in push based ,,, and since we register a listener at the consumer creation and request execution ,, then how can we get the values ??the short answer is via push to consumer,and the long one is a credit based , each consumer has a queue as fallback , its not created when we call next on it our callback will not execut ,its decoupled from next call,, so calling next will increment a credit by one,,, and when we push to the consumer we simply look at the credit and if it is positive then we execute the callback, else we enqueue the value so that the next call of next() will verify the queue and if there is value(s) the callback is executed ,,, you notice that push,next are switching the responsiblity of calling the callback ,,,, this way if the consmer is synchronous it will have always a positive credit before any value pushed to it so push will execute the callback directly and the queue is not envolved that's mean the hot path is preserved like push based systems.
and this is the solution that is superion in my opinion to the previous ones.

Now a question rise "how to handle error?" :
my response is from a long experiment and iteration tell that error handling can and its recomanded to be handled in a outer layer than the core,, the main reason is the components must be dumb and need to know nothing and must be agnostic ,, so like a weak promise aware design ,,the same rules applies,, since error like promise are not always there ,,so they are a special case and if we make our system error aware will imply many branching and much more implementation variants in our components and we can't get a trully pure modules,, and the hot path will be compromised and we pay some extra code execution for no reason ,, if the user write a code that never throw ?? and this is the philosophy "primitives must be dumb and unbounded" if we need bounds or handling errors there will be some other higher level component that are dedicated for that and they will only know about their jobs,
because there is another question that rize "is the consumer queue is bounded??" and you know my answer "No" .. suppose we make the consumer queue configurable, how many options and strategies can have ?? and even if we add them the queue will be a massive and adding a simple config will add complexity ,,, the approach i adopted is simple ,, consumer accept a queue factory ,,now user will provide any queue implementation since consumer rely on an inteface Queue and even if the user can provide its own implementation i discourage it since now users must know about another primitive ,and like i mention before those "stream,pipe,transformers" is the only primitive that the user must know ,, so to respond to the question , we provide a set of transformers to bound the consumer queue, and each transformer hide the queue factory internaly and its only responsible for a strategy , this way we can add on the fly any bound and any behavior withour touching the core code ,, and this is the distilled knowlege i get from my journey ,, the queue bound principle i mention is an example of how many other problem are solved ,, like error handling ,, async workflow using only a single resolve transformer and many other... even the aggregate transformers like sum,max,min,...etc are specialized so that the computation id decoupled from collecting ,,they emit each step and to get the final result you need a specialized transformer `last` that its job is only collect the last value.

now there is another concept i want to point , its `passive` versus `active` consumption,,, the reality is since our system is a pull disguised as push ,we support any type of source, from finit ones like iterables,timeout,...etc to an infinit ones like event emitter or websocket connection,Stream,...etc.
i notice that some sources are `replayable` that mean each consumption is undependent from another one, this mean that the source replay the values.
in this case when we share a source and we have many consumers , which one trigger the consumption ??? my response is all by default so we call them `active` .. any consumer is active by default and the share strategy for my library is like this: the fast consumer trigger the source and slowes ones will get the prefetched values when a shared source broadcast so if the slowest consumers have positive credit they execut immediatly their callback and if not they will enqueue those values and since consumers are hiden from the user by a transformers we can bound their queue by a desired bound trategy and this way the hot path is preserved too,
and the cases that are many who need to add a consumer that must not trigger the source like loggers or somthing like that we simply make them `passive` by adding a dedicated transformer called "passive" and they will recieve values only when their source is pulled by some `active` consumer(s).
so the design is clear now ,, if we want a behavior ,we simply add a dedicated transformer for it
Another thing i want to point is , if the `pull-on-push` is callback based and if it's synchronous, then how we deal with reentrancy problem ?? i have just flatten the execution using a simple check on the credit variable ,and the Consumer code in my repo shows how.
And since transformers are `Source` and need to implement consume method ,and consume must return a consumer and consumer is just an object with push,next,terminate we can delegate its creation safely , take a look a `map` transformer as example ,, the natural flow is to consume from the input source/stream/consumable and push transformed value to new consumer that have the same type as the return type of mapper and we return this last consumer , this solution require two consumers per transformation... but since consumer is immutable in a some sense and if we return the input consumer instead and make the transformation inside it ,, the code that request this consumer will not care which consumer we give it and it simply call next,terminate that are a none value type aware ,we now have a single consumer per transformer that is already requested from the input and that input may already use the same pattern to provid as with that consumer .. so we end up with a nested callbacks calls thet can be easily inlined by the jit. and more importantantly its lazy transducers like pattern out of the box,of course this pattern will colaps when we use `share` but in the most cases we got the performances of transducers and users can build a lighweight pipelines for free
An important desing decision is some transformers can be written by others ones ,but they are written from scratch and for a good reason ,, its to avoid multiple consumers instances ,,, imagine if "range " where written like this "skip(start).pipe(take(offset))" of course its beautiful but not performant as a raw single consumer from the input that provide the transducer like pattern and performances an memory efficiency
